## 1. 项目概述

### 1.1 项目简介

「AI 赋能的校园互助服务平台」面向高校场景，把学生/退休教职工的日常求助（学业答疑、生活互助、后勤维修、官方活动）转化为可追溯的工单，由平台智能解析、风险分级、撮合互助，并以信用积分体系保障互助质量。

平台由三端一后台组成：

| 端 | 入口 | 目标用户 |
| --- | --- | --- |
| 学生端 | `/app/` | 在校学生（移动优先，480px 居中） |
| 适老化端 | `/elder/` | 退休教职工（大图标、高对比度、语音优先） |
| 管理端 | `/admin/` | 平台管理员/学工（看板、复核、规则治理） |
| 后端 API | `/api/v1/*` | 三端统一 RESTful + Bearer JWT |

### 1.2 核心亮点（一句话版）

1. **一句话发布求助**：LLM 解析出任务类型/紧急度/地点/时间，全部槽位人工可核对修改后才提交（AI 辅助不越权）。
2. **RAG 校园知识库问答**：回答基于校园语料检索生成并标注来源，可解释、不编造。
3. **SSE 流式输出 + 思考状态**：逐句渲染，AI 交互体验完整（流式/思考/错误边界/优雅降级）。
4. **Function Calling 工具调用**：LLM 路由到平台工具（查工单/查信用/查知识库），白名单执行防幻觉。
5. **AI 安全纵深防御**：提示词注入清洗 → 规则表确定性 L3 拦截 → 敏感输出过滤，三级防线全留痕。
6. **全链路可降级**：无任何外部 Key 时，规则引擎 + 纯检索兜底，平台功能 100% 可用。

## 2. 需求分析

### 2.1 真实场景与痛点

- 求助信息散落在群聊/朋友圈，**无法结构化、无法追踪、无法评价**；
- 高风险需求（现金交易、代考、代刷）混在正常求助里，**缺乏风控**；
- 退休教职工不会用复杂 App，**适老化缺位**；
- 互助缺乏激励与约束，**帮忙没有回报、失约没有代价**。

### 2.2 用户故事（节选）

- 作为学生，我用一句话描述需求，系统帮我解析成工单，我核对后一键发布。
- 作为学生，我想知道「校园卡怎么补办」，AI 直接告诉我流程并给出来源。
- 作为志愿者，我接单完成互助后获得信用分，信用分越高越容易被推荐。
- 作为管理员，高风险工单自动进复核队列，我可以配置风险规则与积分规则。
- 作为退休教师，我按住说话就能发布求助，字体够大、对比度够高。

### 2.3 非功能需求

- 零外部依赖可运行：无 npm 构建、无外部数据库、无强制 API Key；
- 安全：密码哈希（pbkdf2）、JWT 鉴权、注入防护、敏感过滤、审计日志；
- 可追溯：工单状态机、积分流水（rule_id/rule_version 留痕）、拦截日志。

## 3. 系统架构设计

### 3.1 总体架构

```
┌────────────────────── 浏览器（三端单文件 SPA，零构建） ──────────────────────┐
│   管理端 /admin/          学生端 /app/           适老化端 /elder/            │
└──────────────────────────────────┬──────────────────────────────────────┘
                        原生 fetch · Bearer JWT · RESTful /api/v1
┌──────────────────────────────────┴──────────────────────────────────────┐
│  FastAPI 单进程五服务模块化（P3 可拆微服务）                                │
│  users（鉴权） orders（状态机） ai（解析/RAG/流式/工具） credits（积分） admin（治理） │
├─────────────────────────────────────────────────────────────────────────┤
│  AI 层：GLM-4-Flash（OpenAI 兼容端点，httpx 直连不引 SDK）                  │
│  意图解析 · RAG 问答 · SSE 流式 · Function Calling · 安全过滤               │
├─────────────────────────────────────────────────────────────────────────┤
│  数据层：SQLite（SQLAlchemy 2.0）· 规则表 · 流水表 · 审计日志                │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.2 关键设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 前端形态 | 单文件 SPA（原生 HTML/CSS/JS + Hash 路由） | 零构建零依赖，评委 clone 即跑；接口层统一，P3 可平迁 Vue/TS 工程 |
| 后端框架 | FastAPI 五服务模块化单进程 | 自动 Swagger、类型安全；模块边界清晰，可拆微服务 |
| 数据库 | SQLite + SQLAlchemy 2.0 | 零安装；ORM 屏蔽方言，P3 换 PostgreSQL 零改动 |
| LLM 接入 | httpx 直连 OpenAI 兼容端点 | 不引 SDK 减少依赖面；超时/失败一律返回 None 由调用方降级 |
| 流式方案 | SSE（POST + text/event-stream） | 单向推送足够；fetch+ReadableStream 消费，无需 WebSocket |

（完整决策记录见 `docs/decisions.md`）

### 3.3 数据模型（核心表）

- `users`：多租户字段 tenant_id、role、credit_score；
- `work_orders`：work_order_no、task_type、urgency、location、time_slot、description、status（created→published→accepted→in_progress→completed / blocked）、risk_level、requester_id、volunteer_id、review_record；
- `risk_rules` / `credit_rules`：管理员可配置的规则表（热更新、版本留痕）；
- `credit_ledger`：user_id、order_id、event、rule_id、rule_version、delta、operator；
- `audit_logs`：login/block/review/rule_change/credit_appeal 全留痕。

### 3.4 工单状态机

```
created ──AI分级──▶ published（L1/L2）        blocked（L3，终态+官方渠道指引）
published ──accept──▶ accepted ──start──▶ in_progress ──complete──▶ completed
非合法迁移一律 409 拒绝（有单测覆盖）
```

## 4. AI 技术方案

### 4.1 技术选型理由

| 维度 | 选型 | 理由 |
| --- | --- | --- |
| 大模型 | 智谱 GLM-4-Flash | OpenAI 兼容端点接入成本低；free档成本可控适合校园场景；中文语义理解好 |
| 接入方式 | httpx 直连（不引 SDK） | 依赖面最小；统一封装 glm_chat/glm_chat_json，失败一律返回 None |
| RAG 检索 | TF 余弦 + 2-gram 分词 | 语料小（8 篇）无需向量库即可跑出高召回；接口抽象成 recall(query,k)，P3 平迁向量库 |
| 流式 | SSE | HTTP 语义简单，代理/网关兼容性好 |
| 工具调用 | Function Calling（MCP 风格 schema 注册表） | 工具自描述、白名单执行，安全可控 |
| 降级 | 规则引擎（词表+正则） | 平台在无网/无 Key 环境 100% 可用（R16 熔断降级） |

### 4.2 集成方式

**① 意图解析（/ai/parse）**：用户一句话 → Prompt 约束 LLM 输出 JSON 槽位（task_type/urgency/location/time_slot/description）→ 枚举合法性校验（防幻觉）→ 失败/超时（10s）自动降级规则解析。前端回显全部槽位**人工可改**后确认发布——AI 辅助而非替代决策。

**② RAG 问答（/ai/ask 与 /ai/ask/stream）**：
```
问题 → sanitize_input（注入清洗）→ kb.recall(query,k=3) TF 余弦召回
     → 上下文拼接 Prompt → GLM 生成 → check_output（敏感过滤）→ 答案+sources
     ↘（无 Key/失败）纯检索兜底：直接返回知识库原文片段
```
返回体携带 `mode`（glm/retrieval）、`sources`（召回文档）、`injected`、`sensitive_blocked`，**可解释可审计**。

**③ SSE 流式（/ai/ask/stream）**：复用同一 _rag_answer 生成逻辑，按句切片 delta 事件推送（sources→delta*→done）；注入命中时直接推送拦截提示帧。前端 fetch+ReadableStream 解析 `event:`/`data:` 帧，逐句渲染。

**④ Function Calling（/ai/tools/*）**：
- `GET /tools/list`：MCP 风格工具注册表（search_orders / get_credit / search_kb，含 JSON Schema 参数描述）；
- `POST /tools/call`：LLM 以 System Prompt 路由选工具 → **白名单 `_exec_tool` 执行** → 幻觉工具名直接拒绝；无 Key 时规则路由（关键词匹配）兜底。工具只读、参数校验，杜绝任意执行。

### 4.3 优化策略

1. **分级降级**：LLM 失败≠功能失败。解析降级规则引擎、问答降级纯检索、工具降级关键词路由，三层兜底保证可用性。
2. **Prompt 工程**：槽位解析强制 JSON 输出 + 枚举白名单校验；工具路由 System Prompt 明确「只准从列表选择」。
3. **性能**：glm-4-flash 低延迟；RAG 只召回 top-3 控制上下文长度；SSE 按句推送避免整段等待。
4. **安全纵深**（详见 4.4）。
5. **可观测**：AI 拦截/降级/工具调用全部落审计日志。

### 4.4 AI 安全与可控性

| 防线 | 机制 | 位置 |
| --- | --- | --- |
| 输入侧 | 提示词注入清洗（ignore previous/你现在是/越狱等模式命中即标记 injected 并拦截） | sanitize_input |
| 业务侧 | 规则表确定性风险分级，L3 硬拦截 + 官方渠道指引（管理员可配置规则，热更新） | /orders 发布链路 |
| 输出侧 | 敏感内容过滤（现金交易/代考/刷单等→替换兜底话术，sensitive_blocked=true） | check_output |
| 执行侧 | 工具白名单 + 只读 + 参数校验，幻觉工具名拒绝 | _exec_tool |
| 追溯 | 全部拦截/降级写 audit_logs | 全局 |

## 5. 核心功能实现

### 5.1 一句话发布 + 人工核对（学生端）

语音（MediaRecorder→base64→/ai/asr，Demo 模拟）/ 文字双入口 → 智能解析回显结构化工单 → **全部槽位可改** → 确认发布（POST /orders）。L3 命中直接弹官方渠道指引，不进广场。

### 5.2 互助闭环 + 信用体系

接单（accept，承接者+1）→ 完成（complete，+5）→ 评价（rate，发布者+2、承接者按星级 +1×score 或 <3星 -2）。落账统一走 `_apply_credit`：流水带 event/rule_id/rule_version/operator，**每笔可追溯、可申诉**（POST /credits/appeal → 审计日志）。

### 5.3 管理端治理

看板（今日新增/官方任务/7日趋势/状态与风险分布）→ AI 复核队列（L2 pending_manual_review）→ 订单管理 → 风险规则/积分规则热配置 → 审计日志。

### 5.4 适老化端（对照工信部《APP适老化通用设计规范》2021）

大图标 80px+、基准字号 20px（正文 28px+）、点击区 ≥96px、米白底近黑字对比度 >7:1、行距 1.8；首页仅两大入口、语音优先文字兜底、顶部统一返回。

## 7. 创新点说明

**技术创新**
1. **三级可降级 AI 架构**：LLM→规则引擎、RAG 生成→纯检索、工具 LLM 路由→关键词路由，业界常见的"降级文案"在这里是完整功能等价降级，无 Key 评委环境也能演示全部 AI 流程。
2. **RAG + 来源标注 + 审计字段**：answer/mode/sources/injected/sensitive_blocked 一并返回，AI 输出可解释、可审计。
3. **Function Calling 白名单执行**：工具以 MCP 风格 schema 自描述注册，LLM 只做路由不做执行，防幻觉防越权。
4. **规则表驱动的确定性风控**：L3 拦截不依赖概率模型，规则热更新 + 版本留痕，可复核可申诉。

**应用创新**
5. **AI 辅助而非替代**：解析结果全部槽位强制人工核对修改后才提交，把"AI 幻觉风险"挡在提交前。
6. **校园互助 + 信用闭环**：互助行为即积分事件，流水留痕可申诉，形成正向激励闭环。
7. **适老化互助场景**：把退休教职工纳入互助平台（语音优先+适老规范），覆盖同类作品少有的群体。

## 8. 总结与展望

**总结**：项目在零外部依赖约束下实现了「三端 + 五服务 + AI 深度集成」的完整闭环：一句话发布、RAG 问答、流式交互、工具调用、三级安全、信用体系、适老化改造，全部功能经过端到端实测。

**展望（P3）**
- ASR 接入真实识别（`AIC_ASR_*` 已预留）、LLM 真 token 级流式（前端零改动）；
- RAG 平迁向量数据库（recall 接口不变），语料扩至校规全文；
- AHP 权重匹配引擎落地推荐排序；积分扩展失信惩戒与频次风控；
- 多租户隔离强化（行级 tenant 过滤）；前端平迁 Vue3 + TypeScript 工程化。
